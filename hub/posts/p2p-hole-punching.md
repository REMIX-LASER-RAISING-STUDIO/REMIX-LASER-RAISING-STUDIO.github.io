# 没有服务器的联机：一次握手码，两个 NAT 洞

Minecraft 局域网联机的老问题：只有在同一个 WiFi 下才能互相看见。想跨网玩，得靠内网穿透工具、组网软件，或者干脆租个服务器。

10 月 7 日晚上到 8 日深夜，我们把这条路自己走了一遍——**不用服务器**，两台启动器交换一段码，然后直连。

这是整个项目里最难的一段，也是踩坑最多的一段。

## 23:59 — 先解决四个纯数据问题

第一层不含界面和转发逻辑，只做四件事。

**握手码 `CHERT2:`**

自描述 TLV → Deflate → Base64URL。里面装：nonce、临时 X25519 公钥、本机候选地址、设备名、MC 版本、MC 端口、校验指纹、过期时间（10 分钟）。

为什么不用 CBOR？因为 `System.Formats.Cbor` 是独立 NuGet 而不是框架内置，自写 TLV 更短、离线可验证。

分成 Offer（房主邀请）和 Answer（加入者应答）两种——**没有服务端推进局面**，必须防止用户把对方发来的码粘回自己的输入框。

**密钥交换**

每次连接临时生成 X25519 密钥对，双方用 ECDH 派生会话密钥，握手随机数一并参与防重放。

这里有个 Windows 特有坑：

> Windows CNG 的 X25519 公钥导出是 **64 字节（X‖Y）**，两个坐标必须一起给。`ECParameters` 里只填 `Q.X`、把 `Y` 留空会被直接拒绝。

解法是用 `ECCurve.CreateFromFriendlyName` 逐个曲线别名探测，加两级导入降级。另外暴露 `IsSupported` / `UnsupportedReason`——不支持时给一句人话，别抛异常。

**候选地址**

本机 IPv4、IPv6 公网、UPnP 映射后的公网端点。UPnP 走 SSDP M-SEARCH 发现 IGD，再 SOAP AddPortMapping。

失败就**静默跳过**。路由器不支持 UPnP 是常态，不能因为这一步失败就让整个功能不可用。

**UDP 打洞**

朝对方候选地址持续发包，IPv4 和 IPv6 各一个 socket。`v6` 必须设 `IPv6Only`，否则不能和 `v4` 共用同一个端口号。

socket 生命周期刻意很短：成功后立刻释放端口，上层用同一个端口发起 QUIC。

## 00:00 — 为什么是 QUIC 不是裸 TCP

隧道把 Minecraft 的 TCP 连接塞进 QUIC 双向流。三个理由：

- QUIC 自带 TLS 和丢包重传，而我们手上只有一个 NAT 洞，链路质量没有保证
- QUIC 多流正好映射 Minecraft 会开的多个 TCP 连接
- 自己造 TCP-over-UDP 会踩 TCP-in-TCP 的性能陷阱

TLS 证书每次连接临时自签——它只是「让 QUIC 肯握手」的入场券。**真正的身份验证在应用层**：用 X25519 派生的会话密钥做双向挑战应答，不通过即断。

少了这一步，QUIC 只保证不被偷看，不保证连上的是交换过握手码的那个人。

编排上刻意分两步（先出码、后连接）。没有服务器，双方必须手工传递各自的码，中间人（用户）要花时间发过去、等对方粘回来，三个阶段不能一股脑跑完。

## 00:53 — 没有 STUN 就是瞎打

上一版候选地址只有三种：本机内网 IP、UPnP 映射、用户手填。缺了 STUN，就永远不知道自己在外网被分配成什么 `ip:port`。

邀请码里塞的全是 `192.168.x.x`，对方照着发包必然石沉大海。也就是说当时只有「两边路由器都成功做了 UPnP」这一条窄路可能通。

补上 `StunClient`（RFC 5389 / 8489 的最小子集）和 `NatProbe`（RFC 4787 映射行为判定）。

三个实现决定：

**必须校验魔数和 12 字节事务 id。** 同一个 socket 上可能有别的包，少了这道校验就会把别人的响应当成自己的公网地址。

**用同步 `ReceiveFrom` 加 `Socket.ReceiveTimeout`，不用 `ReceiveFromAsync` + `CancellationToken`。** 因为 Windows 上取消进行中的 IOCP 接收会污染 socket 的后续操作，而判定 NAT 需要在同一个 socket 上连做三四次查询。

**判 NAT 不依赖 `CHANGE-REQUEST`。** 公共 STUN 大多不支持那个扩展属性。改成从同一个 socket 依次问三处——服务器 A、A 的另一个端口、不同 IP 的服务器 B——组合出的差异正好对应三种映射行为：

| 结论 | 直连前景 |
| --- | --- |
| EndpointIndependent（锥形） | 打得通 |
| AddressDependent | 成功率偏低 |
| AddressAndPortDependent（对称 NAT） | 几乎不可能，应趁早劝退 |

全部服务器无响应时，判定为「UDP 出不去」，给专门提示而不是笼统失败。

## 01:27 — 真机两处，以及 7% 的静默放行

写完只在脑子里验过的代码，一跑就露馅。

**第一处**：NAT 探测在本机完全失败，还报错成「UDP 出不去」。可实际上 UDP 一路畅通，`stun.miwifi.com` 立刻就回了。两个原因叠着：

- `stun.l.google.com` 解析出的第一条是 IPv6 记录，而探测 socket 是 IPv4，`SendTo` 直接 `AddressFamilyNotSupported`。候选列表要按地址族过滤
- 第一台服务器失败就当成「全部失败」下结论。改成最多试三台，并把最后一次的真实错误带进提示

笼统一句「UDP 被挡」会把人引向完全错误的排查方向。

**第二处**，这个更值得说：

> 握手码被改动后，有 **7% 的概率被静默接受**。

原因是校验只覆盖「解压出来的内容」。改动如果落在解压器根本不读的冗余字节上，解压结果一模一样，于是整段通过。

修法是在码尾加 `<载荷>.<6 位检错码>`，检错发生在解压**之前**且覆盖实际字节。400 轮压测从「30 次放过」变成「0 次放过」。

## 01:28 — 二维码根本扫不出来

隧道从 App 层挪进 Core（它本来就只依赖 BCL 和 `P2PIdentity`），于是能进单测。7 项自测：隧道自环、多条 TCP 不串数据、会话密钥不一致时被挑战应答挡下、两个打洞器互发、停止后端口立刻可重绑。

然后顺手验证了一件此前从没人验证过的事：

> 握手码编码出来是 **69×69 模块**（版本 13）。界面那个 136px 的方框下，每个模块不到 2 像素，手机根本扫不了。

二维码组件从 WPF 里拆出来（改 `PngByteQRCode` 自己拼 PNG，不碰 `System.Drawing`，没有 DPI 缩放和句柄泄漏）。界面方框放大到 320 让二维码独占一行，每模块约 4.6 像素。用 ZXing 解码验证，内容与原文一致。

还有个细节：`QRCoder` 的模块矩阵本身已含静区（外面 4 圈全白），自适应时不能再自己加一遍，否则 scale 偏小、图会糊。

## 23:08 — 连上之后怎么办

最后一轮，全是上一次真机跑通之后才暴露的问题。

**保活与断链。** 隧道协议加 1 字节通道号（`1` = 转发数据 / `2` = 心跳）。原来每条 QUIC 流都被当成 Minecraft 数据直接往本机 MC 端口塞，没有第二条路可用。

加入者每 15 秒发一次心跳。为什么？NAT 的 UDP 映射 30~60 秒没流量就被回收，而 MC 在加载地形、切维度时十几秒没数据是常态——不补心跳，洞就没了。

连续 3 次心跳没回音才判死（约 50 秒），避免单次丢包就误报。

房主不主动发，改由看门狗盯「多久没动静」（60 秒）。它是被连的一方，对端拔网线时 QUIC 不会立刻报错，只有静默时间能说明问题。`LinkLost` 事件只报一次，因为心跳超时和看门狗可能同时到达。

**不换码重连。** 抽出 `EstablishAsync()` 让房主和加入者共用。两个码都还在有效期内就可以重打洞，省掉两边各复制一次两百多字符。

停隧道后强制等 **300ms**。QUIC 释放端口不是瞬时的，急着打洞会撞上「端口被占用」——而这个症状跟「路由器不支持直连」长得一模一样，极难排查。

**打洞预算从 12 秒放宽到 20 秒。** 真人复制一段码再切回窗口点击，差几秒太正常。

顺便做了三件收尾：打洞端口不再写死（`PickFreeUdpPort` 往后挑一个能绑上的）；`Reset`/`Dispose` 撤回 UPnP 映射，不在路由器上留渣；失败时按「最可能成功」给具体下一步——同网段 → IPv6 → UPnP/公网 IP → 组网工具。
